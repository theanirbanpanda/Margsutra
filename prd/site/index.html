Margsutra · Product case study · 2025

Keeping trekkers visible when the signal disappears.

Margsutra is a safety-first expedition platform for guided treks. I ran 15+ trekker interviews, wrote the PRD and shipped the system: live tracking, an SOS that leaves the device over three independent transports, and a SAR console that owns an incident from trigger to closure.

01 Problem

The map ends where the signal ends.

A guided trek is 10–30 people, one to three leads, and a route that loses cellular coverage for hours. The tools a lead actually has — WhatsApp, a paper roster, a phone call — all assume a signal the terrain does not provide.

Safety becomes a headcount at a checkpoint. Medical data sits in a form nobody can open in the field. When something goes wrong, five people call five other people, nobody owns the response, and nothing is recorded afterwards.

02 Research

What the interviews changed.

The job wasn’t digitising a booking form. It was maintaining command when the network disappears.

AssumptionWhat we heardDecision
Digitise bookings, add a weather dashboard. Booking is already solved on WhatsApp. Nobody could tell me where the group was. Safety and visibility became P0. Booking and weather became table stakes.
SOS should call emergency services. Leads want to handle it internally first. Escalation is a phone call they make once they know where to send people. Built a command console with ownership and a record, not a 112 integration.
Offline maps solve the dead zone. A map doesn’t tell you who is missing, or since when. Tracking, roster freshness and a multi-transport alarm — in that order.
03 What shipped

Four systems, one loop.

See the person, hear the alarm, own the response, close the record.

01 / Visibility

Live expedition map

Socket.IO position telemetry on a Leaflet map, with explicit freshness, roster status, group proximity and a per-trip safety perimeter. Stale data is never rendered as live.

Socket.IOLeafletJWT
02 / SOS

An alarm that survives

SOS fans out over WebSocket, REST and Firestore, with per-transport delivery state. If all three fail, a localStorage outbox retries until one lands — and a stand-down can never be resurrected by the retry loop.

3 transportsOffline outboxIdempotent
03 / Command

SAR incident lifecycle

An event-driven console with an incident feed, medical profile, one-tap dialing, and an explicit acknowledge → resolve lifecycle. Acknowledgement records ownership; only a resolve closes the incident, with resolver, time and notes.

ExpressFirestoreState machine
04 / Off-grid

LoRa field relay

ESP32 nodes send GPS, weather, air quality and SOS over SX1276 LoRa with a send-then-listen ACK window. A gateway bridges LoRa into Firebase Realtime Database and polls downlink commands such as a remote siren.

ESP32SX1276RTDB
04 Decisions

What I cut, and why.

Every cut below is a second system that would have delayed the loop that matters.

One deploy unitover Cloud Functions

Firestore triggers were prototyped, then cut. The shipped event path is an Express service writing to Firestore and broadcasting over Socket.IO.

Trade-off: less elastic, but one container, one health check, local parity, and a free tier that stays up.

Client-side perimeterover server geofence

Breach detection runs on the device from the latest fix. It works with no signal and no round trip.

Trade-off: the console does not receive breach events yet. That is P1 and written down, not hidden.

Honest “queued”over optimistic “sent”

Delivery state is per transport: sent, queued or failed. “Sent” only appears when at least one transport confirms.

Trade-off: a scarier UI in the moment — and the only defensible one in an emergency.

Hardware is additiveover hardware-first

The software path must be useful before an operator buys a node. LoRa extends range; it is not a prerequisite for the product to work.

Trade-off: slower hardware story, faster adoption and a smaller support surface.

05 Architecture

Two lanes, one console.

Connected lanephone · HTTPS / WSS
Trekker app→ Caddy→ Express API+ Socket.IO→ Firestore

Durable records in Firestore. The API is the identity authority; the tracking service mints short-lived socket tokens from the same JWT.

Off-grid laneno cellular required
ESP32 node→ SX1276 LoRa→ Gateway→ Realtime Database→ SAR console

The node transmits a JSON payload with GPS, sensors and SOS, then listens for an ACK. The gateway persists telemetry and polls downlink commands.

Resiliencewhen the network is not there
Service worker→ IndexedDB queue→ Background Sync→ /location-batch

Positions are batched and replayed, so an hour in a dead zone arrives as a complete track — not a gap followed by duplicates.

06 Metrics

One number that matters.

Time from SOS trigger to first acknowledgement. It forces both the device path and the console path to work.

North star · pilot target

SOS trigger → first acknowledgement

<60seconds, median
≥99%alerts delivered on at least one transport
≥90%active minutes with a fix under 2 minutes old
<8%battery per hour while tracking
<5%false alarms cancelled inside 30 seconds

Pilot targets — not field-proven results.

07 Status

Shipped, prototype, next.

The line between a working demo and a field-ready product, stated plainly.

Shipped

  • Live tracking and roster freshness
  • Per-trip perimeter and client-side breach state
  • Three-transport SOS with offline outbox
  • Acknowledge → resolve incident lifecycle
  • Booking, rosters and medical profiles
  • ESP32/LoRa firmware and RTDB relay

Prototype

  • BLE wearable pairing — simulated vitals, not hardware-validated
  • LoRa link implemented, not field-validated
  • Single-operator deployment on a free tier

Next

  • Server-side breach events to the console
  • Dispatch assignment with owner and ETA

  • Push notifications and SOS without a session
